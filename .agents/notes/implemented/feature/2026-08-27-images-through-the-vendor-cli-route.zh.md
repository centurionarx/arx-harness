# Agent Note：图片经由厂商 CLI 路由

Status: implemented

[English](2026-08-27-images-through-the-vendor-cli-route.md) | 中文

## Problem

厂商 CLI 路由以 `UNSUPPORTED_CONTENT` 拒绝了每一个 image 块。这看起来像 CLI 的限制，其实不是：它是本适配器如何开启一次运行所带来的后果。

当每一步都拥有自己的运行时，文本记录被压成了一个提示词**字符串**，而字符串只承载文本。于是，由订阅带来可达性的那条路由——没有 API 密钥的用户实际拥有的那一条——恰恰成了唯一读不了截图的路由。

## Decision

SDK 的 `prompt` 不止接受字符串，也接受由用户消息组成的异步可迭代对象。现在一次运行以一条结构化用户消息开启，其内容就是渲染后的文本记录：先前回合是带标签的文本，附件所在之处是真正的 image 块。

图片字节经 `readImageRequest` 取自 `ctx.attachments`，与 HTTP 适配器使用同一个存储、同一套归一化。厂商写明的像素与字节上限是固定常量而非配置：超出它们编码只会产生一个被提供方拒绝的请求，而不是更慢的请求。

哪些模型接受图片是按模型配置的，默认为 false。CLI 不暴露任何目录，因此必须由路由声明；在拒绝图片的模型上声明它，会把每一张附加的图片变成失败的请求，而不是被拒绝的附件。声明了的模型会报告 `inputModalities: ['text', 'image']`，而这正是 Web BFF 在允许附加图片之前所读取的内容。

## Consequences

仍然是每一步一条运行，仍然没有活跃对话——本次改变的是开场消息承载什么，而不是由谁关闭工具调用。当初迫使采用逐步运行的死锁未被触及。

没有挂载附件存储的组合服务于纯文本路由；到达这类组合的图片会以「缺少存储」为名失败，而不是被悄悄丢弃。

非图片的文档——pdf、xlsx、docx、pptx——仍然没有任何表示形式。附件缝合面自始至终是围绕图片成形的（`ImageAttachmentRef`、`ImageMediaType`、`image` 内容块），因此承载它们是对那个缝合面的另一次改动，而不是对本适配器的改动。

## Alternatives considered

**先泛化附件缝合面。** 承载文档意味着 `ImageAttachmentRef` 变成 `AttachmentRef`，并且每个 LLM 适配器都要学会拒绝或承载一种新块类型。图片本来就有一条贯穿缝合面的完整路径，只有本适配器自身的渲染挡住了它们，因此加宽缝合面会是一次庞大却解决不了本问题的改动。

**提取图片中的文字并作为散文发送。** 这需要本仓库并不具备的 OCR，而且恰恰丢弃了用户附上截图所要传达的东西。

**保留字符串提示词，把图片以 data URI 形式附在文本里。** 模型会把 base64 当作字符来读，把上下文花在它看不见的字节上。
