# Agent Note: Codex sign-in from a remote browser

Status: implemented

## Problem

[Native product accounts and the chat card](2026-09-24-native-account-and-chat-sign-in.md) let a person start a Codex browser sign-in from a harness host with no desktop session of its own — a headless Linux server, a container, or a host reached only by SSH. The pinned Codex app-server serves that sign-in's callback at `http://localhost:1455/auth/callback` on the harness host, so completing it from a remote browser needed a forwarded port, and the [remote-access guide](../../../../docs/user/guide/security.md#remote-access-through-ssh) named only that one port. The app-server moves to `http://localhost:1457/auth/callback` when 1455 is already taken on the host, so a tunnel built from the documented port silently stopped working, and neither card offered a route around forwarding at all. Device-code sign-in already worked without a forwarded port, but both cards listed browser first even on a host that cannot open one, and neither said forwarding was even in play.

## Decision

The native Codex driver (`packages/credentials/native-accounts/src/drivers.ts`) reads the sign-in's return address from the authorization address's `redirect_uri` query parameter, and only when that value parses to `http`, a `localhost` or `127.0.0.1` host, and an explicit port; a login whose authorization address names anything else, and every device-code login, asks the person nothing extra. For a matching browser sign-in, the attempt prompts with input `redirect-url` for the address the person's browser ends on, in parallel with the browser step. A pasted address must repeat the return address's protocol, host, port, and path and carry a non-empty query; arx then forwards only that query to `http://127.0.0.1:<port><path>` on the harness host, with `redirect: manual`, because the app-server's callback listener binds the IPv4 loopback address while `localhost` may resolve to `::1` first. A response below 400 ends the relay, and the app-server completes the sign-in as if the browser had reached it directly; a refused or unreachable listener, or a paste that does not match, asks again until the attempt settles (`packages/credentials/native-accounts/src/types.ts` adds `NativeLoginInput`; the manager and the `nativeAccounts.*`/`authorization.*` wire schemas carry it end to end).

The Models page reads the connection's host description before ordering either sign-in card. A connection whose `hostDescription` reports `canOpenPath: false` — Linux with neither `DISPLAY` nor `WAYLAND_DISPLAY`, or `apiProxy.nativeOpen: false` — makes the **Native product accounts** card list device-code sign-in before browser sign-in for Codex (Claude Code offers only browser sign-in) and show a notice, and makes the **OpenAI Codex chat models** card show a notice of its own; a native attempt asking for `redirect-url` renders a field for the return page's address, and the chat card's already-generic prompt field carries the analogous pasted address the `openai-codex` authorization flow's own browser method can ask for. Each card cancels its own attempt when the Models page closes, so the sign-in tab stays open and reachable while a person works through it. The attempt deadline stays the existing one: native `loginTimeoutMs` and apiProxy `authorization.attemptTimeoutMs` both default to 600 seconds.

## Alternatives considered

**Forwarding the callback port only, left as the sole documented route.** Fixing the guide to also forward 1457 keeps working on a host the person can already tunnel into, but a Windows host that reserves 1457, or a person who cannot add a second forward, would still be stuck; it also does nothing for the "list device-code first" gap the host description now covers.

**Auto-answering the chat card's login-method question.** The `openai-codex` flow's method choice is one of pi-ai's own prompt options; picking it from this package would couple the client to option ids the flow does not export as a public contract, and a future flow change would break the coupling silently instead of through a typed surface.

**`launchedThroughSsh` as the remote signal.** A process fact of this kind reads false under a systemd-managed host reached over SSH, which is a common deployment for exactly this scenario, and it would add a dependency from account sign-in to how apiProxy was started rather than to what the browser can reach.

**A new host fact naming "browser on loopback".** `canOpenPath` already reports whether the connection can open a local path in a desktop session, which is the same fact a Codex browser step needs; a second fact with no other consumer would duplicate it for no gain.

**Exposing the callback listener with `PI_OAUTH_CALLBACK_HOST=0.0.0.0`.** The browser still targets `localhost`, not the harness host's address, so a bound-everywhere listener would not make a remote browser's callback reach it; only relaying the browser's own final address, as the person sees it, closes that gap.

**Writing Codex credentials through the app-server's token method.** The pinned app-server owns Codex's credential file; teaching arx to write it directly, instead of relaying the callback query the app-server already expects, would make arx a second writer of a credential [`packages/credentials/native-accounts/src/index.ts`](../../../../packages/credentials/native-accounts/src/index.ts) documents as owned solely by the native tool.

## Consequences

A host reached only by SSH, with no desktop session and no forwarded port, can still finish a Codex browser sign-in: the person opens the sign-in link the harness host cannot reach, and pastes back the address it lands on. A host with its own desktop session, reached remotely, is unaffected: it still lists browser sign-in first, and the same paste field is still available if a person prefers it over opening a local browser. The pasted address carries a one-time authorization-code query; it crosses only the already-privileged loopback account RPC, and arx forwards it only to the loopback port and path the sign-in itself named, never elsewhere. A person mid-sign-in must keep the Models page open, since either card's attempt is cancelled the moment that page closes.
