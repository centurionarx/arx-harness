# Agent Note: Each session keeps its own model selection

Status: implemented

## Problem

A session's model selection was a process-local override in an api-proxy `WeakMap<Agent, ModelSelectionRef>` ([session model selector](2026-07-24-web-session-model-selector.md)), durable only once a request actually consumed it into a logged `request/header` ([default follows the picker](2026-08-07-default-model-follows-the-picker.md)). Every accepted pick also unconditionally saved the shared deployment default. Two effects followed. First, a session whose pick never reached a request — a blank session, or one picked right before a Host restart or an ApiProxy service reload — lost that pick: a fresh `Agent` object has no WeakMap entry, `selectionFor` fell through to the logged `request/header` (absent) and then to the live shared default, which by then could be a different session's last pick. Two users, or two tabs, picking different models therefore appeared to "swap": whichever session's pick was made last became every unconsumed session's effective model. Second, `resolveChildAgentOptions` seeded a subagent child from the parent `Agent`'s fixed, construction-time `options.provider/model` — itself seeded from the shared default at create/resume/fork time — so a child could spawn on a different session's last pick even while its own parent was correctly routing its own requests.

## Decision

`SessionEventMap` gains `'model/selection'` (payload `ModelSelection`, declared in `packages/core/agent/src/model-selection.ts` next to the type it names), a required, log-only event: it never enters the derived model transcript — `request/header` keeps recording the config a request actually used — and `SESSION_FORMAT_VERSION` does not change, since it is new vocabulary, not a structural change.

`session.selectModel` appends `model/selection` to the addressed session's own log immediately after validation succeeds, before installing the in-memory override and before saving the shared default (still on every accepted pick, unconditionally — decision: a new session keeps seeding from the last pick made anywhere). A pick equal to the session's current effective selection appends nothing: a repeated identical pick must not grow a still-blank session's stored artifact for no semantic change (see Consequences).

The effective selection a session resolves on every read is now, in order: a selection made in this api-proxy process for the live `Agent` object, otherwise the session's own latest logged `model/selection` not superseded by a later logged `request/header` (log order, not event type, decides), otherwise that latest `request/header`, otherwise the live shared default. `foldSessionModelSelection(events, from?)` is the pure fold (mirrors `foldRequestHeader`); `loggedModelSelection(session)` is its session-keyed incrementally-cached wrapper (mirrors `Session.requestHeader()`), so a per-step read while nothing new was appended costs O(1) rather than a rescan — the api-proxy `selectionFor(agent).current` getter already re-derives on every read while no in-process pick has been made, so an O(n) fold there would have made a long-lived resumed session pay for its whole history on every step. Because a fresh `Agent` for a session starts with no in-process override, this restores the session's own selection whether the gap was a Host restart, an ApiProxy service reload, another browser tab, or a resume: `installSelection` already ran `selectionFor` on every session create/resume/fork path before this change (the WeakMap install was already unconditional), so no new call site was needed there.

`session.fork`'s seed already carries every event up to its boundary, so a source session's `model/selection` picked between turns (the common case: a blank session, or a switch prepared before the next prompt) reaches the child for free once it is logged — no fork-specific code changed. Subagent delegation needed its own fix: `installModelSelection(agentCtx, selection)` now also registers `selection` in a module-level `WeakMap<Agent, ModelSelectionRef>` when `agentCtx.agent` is set, and the new `installedModelSelection(agent)` reads it back. `resolveChildAgentOptions` (`packages/subagent/subagent/src/child-agent.ts`) reads the parent's live installed selection for provider/model, falling back to the parent's fixed `options` only when none is installed (every subagent child today, since children install no live override of their own — the fix is transitive through however many delegation levels deep, because each level's `options` was already resolved correctly at its own construction). `maxTokens` has no live-selection counterpart and still comes from `options`. `continuation.ts`'s subagent-descriptor snapshot (informational, for cold-resume display) now reuses the same resolved `AgentOptions` instead of recomputing provider/model from `parent.options` a second time, so it cannot name a route the child does not actually run.

## Alternatives considered

**Keep the WeakMap the only durable-enough store, and only fix subagents.** Rejected: it does not survive a Host restart or ApiProxy reload, which is exactly the owner's report — two sessions picking different models "swap" after either one's pick falls out of the process-local cache.

**Always append `model/selection`, including an identical reselect.** Rejected: appending on every reselect (including a re-affirmed inherited default) risks a still-blank, list-hidden session's stored artifact crossing `coldBlankProbeMaxBytes` (`DEFAULT_COLD_BLANK_PROBE_MAX_BYTES`, 1024 bytes) after enough picks; past that, `probeColdSessionMetadata` declines and `summarizeCold` reports `blank: false`, so the session stops being blank-reused by New Session and starts appearing in a cold sidebar. `modelSelectionEquals` skips the append when the incoming pick already matches the session's effective selection, which is the actual growth source (a no-op reselect changes nothing); it does not bound growth from alternating between two distinct models on one still-blank session, which is out of scope for this change and remains possible in principle.

**Extend `agentOptions()` (api-proxy) or `ApiRemoteAgentOptions.agentOptions` (agent-lookup.ts) to seed a top-level session's construction-time `AgentOptions` from its own log instead of fixing subagent delegation.** Rejected as the primary fix: every top-level session create/resume/fork path already runs `installSelection` before publication (via `composeAgent(...).setup`), so `selectionFor`'s live derivation already overrides the fixed `options` for a top-level session's own requests regardless of what seeded them; the actual gap was that `resolveChildAgentOptions` bypassed that live derivation entirely and read the parent's fixed `options` directly. Fixing the narrower, actual read site is smaller and does not touch `agent-lookup.ts`'s cross-package signature.

**Persist every click as a new session event** — the alternative the session-model-selector note rejected, on the grounds that an unconsumed choice does not reconstruct a model request. That reasoning covered the model-visible transcript, which is still true: `model/selection` does not enter derived history, and `request/header` remains the sole record of what a request used. It did not cover cross-process/cross-restart durability of the session's own preference, which is the defect this note fixes; the two records now coexist, log order deciding which is effective.

## Consequences

Two sessions (or tabs) can each hold a different model indefinitely, surviving a Host restart, an ApiProxy service reload, resume, and fork, without either affecting the other or the shared default drifting them back together. A new session still seeds from the last pick made anywhere (unchanged). A subagent — one-shot or continuable, at any delegation depth — now follows its live delegating parent's current model rather than whatever the shared default was when that parent's `Agent` was constructed.

The blank-session byte-growth risk is bounded, not eliminated, by the dedup: a session alternating between two (or more) distinct models while still blank can still cross the cold blank-probe's byte ceiling and misreport as non-blank after a restart, same as any other event family already able to do this. `packages/host/apiproxy/tests/api-proxy-models.spec.ts` pins the dedup (exactly one `model/selection` event per accepted, changed pick) and the blank-preserving fact; widening the byte-ceiling mitigation itself is out of scope here.

## Testing

`packages/core/agent/tests/model-selection.spec.ts` covers the pure fold, its incremental cache, the equality helper, and `installedModelSelection`'s registration/dispose lifecycle. `packages/host/apiproxy/tests/api-proxy-models.spec.ts` covers two sessions keeping distinct selections with the shared default following the last accepted pick, exactly one logged event per accepted pick (none on rejection or an identical reselect), a later logged request superseding an unconsumed pick and then outranking a later default change, and a blank session's pick surviving a from-scratch ApiProxy generation over a shared store (the restart case). `packages/host/apiproxy/tests/api-proxy-fork.spec.ts` and `api-proxy-blank.spec.ts` cover fork inheritance of an unconsumed pick and blank-preservation respectively. `packages/subagent/subagent/tests/child-agent-model-selection.spec.ts` covers `resolveChildAgentOptions` preferring the parent's live selection, tracking it as it changes, and still honoring a per-request override.
