# Agent Note：平台差异在用户层做导览，事实仍归各自的包所有

Status: implemented

[English](2026-08-28-platform-differences-orient-in-the-user-tier.md) | 中文

## 问题

每一项 Windows 专属契约其实都已有文档，却没有一项是找得到的。

shell 的平台开关写在 base bundle 的 README 里，写受限令牌的边缘情形写在 ACL sandbox 的 README 里，进程树终止与整个控制台范围的中断写在本地 subprocess 提供方的 README 里，日志物化写在 JSONL 后端的 README 里，被跳过的凭据 mode 检查写在本地凭据提供方的 README 里。一个正在决定是否要在 Windows 上运行 harness 的人，得读完五个包的 README，而且还得事先知道该读的正是这五个。用户层则完全没有提到 Windows。

最直观的补救——把 Windows 的行为写进用户指南——会为五项本已有归属的契约再造一个家，而这两份副本会在任何一个后端变动时立刻发生偏离。

## 决定

[平台支持](../../../../docs/user/guide/platforms.zh.md)是一页导览，而不是第二个家。它说明有哪些差异，按读者真正会问的问题分组（用哪个 shell、什么被限制、我取消时会发生什么、什么是持久的、什么不被强制），并把每一项链接到拥有它的包。页面上的每一处技术主张，距离它的权威来源都只有一次点击。

这一页是 reference，不是 tutorial：它回答查找，页面上没有任何内容需要按顺序阅读。

撰写过程中发现的两处缺口，是在各自的家里补上的，而不是写在这一页上。profile 的模块兜底目录把自己描述为"每个包一个符号链接"，而它在 Windows 上创建的是 junction——这个区别正是安装无需提权的原因，因此它属于 `app-boot` 的 README。凭据与物化方面的差异在各自的家里本就已说明，这里只做链接。

## 备选方案

**放在 `docs/subsystems/` 页面。** 子系统页属于 reference 层，完全承载得住这些内容。已否决：正在为 Windows 做决定的读者是产品使用者，而不是要改动 `packages/` 的人，而子系统层的范围是类型定义与语义，不是部署后果。

**在每个拥有者 README 里各写一节平台说明。** 它们本来就存在——这恰恰是问题所在：缺的从来不是内容，而是一页把它们汇集起来。再往各个 README 里加文字只会加深同一个问题。

**交给根 README。** 根 README 是"立刻跑起来"的页面；一张平台矩阵放在那里，会与读者需要的第一条命令争夺注意力。

## 影响

后端变动如今只需更新一个包的 README；只有当它所支撑的那句摘要变得不实时，才需要再改平台页上的一句链接文字。`verify-md-links` 会在被链接的家被重命名或删除时失败，因此这一页不可能无声地活得比它的权威来源更久。

该页是双语的，并已在 [website/docs.ts](../../../../website/docs.ts) 的 Guide 分区注册，因此它承担每个用户层页面都要付出的配对成本。
