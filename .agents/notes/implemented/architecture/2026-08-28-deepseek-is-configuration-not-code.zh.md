# Agent Note：DeepSeek 是配置，不是代码

Status: implemented

[English](2026-08-28-deepseek-is-configuration-not-code.md) | 中文

## 问题

有两个包的存在只为对接一家厂商：`arx-llm-deepseek`，一个手写的 chat-completions 适配器，自带 SSE 分帧、文件 API 与上传索引；以及 `arx-web-search-deepseek`，一个绑定同一账号的搜索提供方。围绕它们，仓库长出了一整套点名该厂商的默认：随附的适配器条目、随附的默认模型、随附的搜索提供方、带厂商专属卡片的引导对话框，以及一个 SDK server——只要调用方给出的提供方它不认识，就替对方挂载该适配器。

[不随附默认模型](2026-08-27-no-shipped-default-model.zh.md)与不随附提供方已经移除了组合层面的默认。剩下的是代码：一个需要持续维护正确性的第二适配器，以及出现在部署方无法更改之处的厂商名称。

`arx-llm-pi-ai` 本来就能抵达同一个端点。它的 profile 映射既接受目录路由，也接受手工声明的 OpenAI 兼容网关；而 pi-ai 自带的 `deepseek` 目录路由，承载的正是那个专用适配器所服务的同一批模型 id。

## 决定

两个包都被删除。想要这家厂商的部署，像对待其他任何提供方那样写一段 profile：

```yaml
- id: llm
  name: '@arx-ai/arx-llm-pi-ai'
  config:
    providers:
      deepseek:
        apiKeyEnv: DEEPSEEK_API_KEY
```

厂商名称只在它指代第三方事实之处保留——路由键、模型 id、环境变量——除此之外一律不留。这些不是品牌，改掉它们只会描述出一个并不存在的端点。

SDK server 不再替调用方挂载任何东西。`initialize` 过去会在组合未为所请求的提供方提供路由时挂载那个专用适配器，于是点名该厂商的调用方会拿到一个自己从未配置过的适配器。现在它直接拒绝，因为未为所请求提供方提供路由的组合，就是一个配置错误的部署。

原先驱动专用适配器的场景改为驱动一条声明式 pi-ai 路由。若某场景的端点是它自己的 mock 服务器，则该路由被整体声明出来——`api`、`baseURL`、`compat`，以及该场景点名的模型 id——而不是从一份描述真实提供方的目录继承而来，毕竟该测试从不真正拨打那个端点。

## 备选方案

**保留适配器，只移除默认。** 什么都不会坏，双适配器对照测试也能保住它的第二个实现。已否决：第二个适配器意味着第二套需要保持正确的协议实现，对分片转换或推理强度的每一处修复都得落地两次。

**把路由与模型 id 改成不含厂商名。** 那样仓库里就一处名称都不剩了。已否决：`deepseek-v4-pro` 正是端点所应答的那个 id。改成别的名字，只是一句部署方还得再翻译回去的谎话。

**用另一家厂商重新录制 replay fixture。** 无密钥快照的头部携带着该厂商的模型 id。暂时否决：重新录制需要替代厂商的密钥，而 replay fixture 中的 id 指代的是一次被录下的对话，并非随附默认。

## 影响

干净截断的 SSE 流现在会走完而不再失败。专用适配器把它报告为 `STREAM_CLOSED`，该码不在默认可重试集合内，因此该轮以错误告终；pi-ai 把同样的截断表述为传输失败，而传输失败默认可重试，于是请求被重新发出、该轮得以完成。`transport-recovery.spec.ts` 固定了这一新行为，并点明了这处变化。

`packages/client/ui-settings-models` 中仍留有厂商专属的引导对话框与一套以已删除 namespace 为键的精选卡片布局。它们针对的是没有任何组合会注册的 namespace，属于死路径；移除它们是本文未覆盖的后续工作。

真实 API 的 e2e 场景仍通过各自声明的路由解析 `DEEPSEEK_API_KEY`，`e2e` CI 作业也仍需要该 secret。把它们指向另一家厂商，如今是每个场景里改一段配置，而不是改代码——这正是本次变更的意义。
