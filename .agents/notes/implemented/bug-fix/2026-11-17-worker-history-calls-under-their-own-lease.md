# Agent Note: Worker history calls carry the capability of their own request

Status: implemented

## Problem

The isolated project worker held one history capability, rebound it on every workspace-scoped request, and sent every broker call with the latest bound capability. Control refuses a capability whose lease is gone, and it deletes a lease when its request answers with a quiescent receipt. Each worker request flushes every session before it answers, and opening a session sends several workspace-scoped requests at once (blank session creation, history, command list, model list). A flush or deferred append of one request could therefore carry the capability of another request that had already answered: control refused it with 403, the worker request failed and the page's request answered 502. In the native identity fixture the resumed session was then unusable in its worker in about a quarter of cold opens: the seeded history did not render, or the session agent or the worker's LLM service was gone.

## Decision

Decided by the owner on 2026-11-17.

- `OwnedWorkerPersistence.runBound(capability, scope, work)` validates and binds the capability and runs `work` in an `AsyncLocalStorage` scope. `call()` uses the scope's capability and falls back to the latest bound capability outside any bound request, such as at worker mount or for an unscoped request.
- The [worker boundary](../../../../packages/host/isolated-project-runtime/src/worker-boundary.ts) runs every workspace-scoped request through `runBound`. Broker calls the request makes, the SSE loop of a stream request (it runs in the stream's `start`) and a turn that a prompt starts continue in that scope. Control keeps those leases valid while the request runs and, after a non-quiescent answer, until it cancels the operation.
- The session write-behind lets a request join a flush barrier that another request opened, and the barrier's writes carry the opener's capability. `call()` records, in a module-private `WeakMap` keyed by the error, the capability that each refused broker call carried, and `refusedAnotherLease(error)` tells whether that capability differs from the current bound request's own. When control refuses a write that carried another request's capability, for any reason, for instance after it cancelled the opener's stream lease on a page reload, a caller whose own operation is still live flushes the session once more under its own capability; the failed batch is still queued, so the second flush sends it again. The opener's refusal is of its own capability, so it never retries under its released lease, whatever its request signal says; a refusal of the caller's own capability, such as a failed durable append, still fails the request and withholds its receipt, and a caller whose request signal is aborted does not retry.
- Control can commit an append and still refuse its receipt: project-storage `append` revalidates the authority and checks cancellation after the commit, and the broker authorizes again after the job. The worker's cursor then stays behind the log, and every later flush of that session used to fail with a sequence mismatch until the worker reloaded it. The broker now appends through project-storage `executionAppend`, which skips leading events that the log already holds with the same content and appends only the rest, so the next flush, or the retry above, writes the batch without storing it twice; a held event that differs still fails on the provider's sequence check. The general `append` keeps refusing a held batch, as its existing callers and tests expect.
- [worker-boundary.host.spec.ts](../../../../packages/host/isolated-project-runtime/tests/worker-boundary.host.spec.ts) pauses an export's broker call while a later control request binds its capability and answers quiescent; the export answered 500 before the change and answers 200 after it. Two more cases hold a session's first append, send it under the capability of a lease control already released, and wait until the test's request joined that flush: a live request answers 200 and the event is stored (it failed before this retry); a request whose operation is cancelled meanwhile rejects, and the next live request stores the event (it failed without the signal check). Those two cases assume that the request's flush starts before the 200 ms write-batch timer fires. A further case lets control commit an append and then refuse it, and checks that the next flush stores the event exactly once (it failed with a sequence mismatch before the idempotent append); [broker-cancellation.spec.ts](../../../../packages/identity/project-storage/tests/broker-cancellation.spec.ts) covers the resend, the identical resend and a differing event at project-storage level.

## Alternatives considered

**Track live capabilities in the worker and use the most recent one.** The worker cannot observe when control releases a retained lease: the native test supervisor aborts a request's signal whenever its HTTP exchange closes, quiescent or not. The most recent live capability can also be released between the choice and the call.

**Hold the page's concurrent reads until the session opens.** In the native scenario the held reads then landed between the hydration and the deferred flush, and the first open failed more often.

**Let control accept a released capability from the same worker.** It weakens the lease rule that makes cancellation and revocation final.

**Give each request its own flush barrier.** The session write-behind owns the barrier and is shared persistence code outside this package.

**Flush again after any failure of the request's own write.** A failed durable append under the request's own capability must withhold its receipt (native-worker.spec.ts); a retry would hide it. A failure of a write under another request's capability is retried whatever its cause, because only the request's own lease can then be trusted.

**Return the receipt of every committed append.** It would move project-storage's post-commit revalidation and cancellation checks out of the receipt path; the idempotent append keeps those refusals and recovers at the next write instead.

**Decide the retry from the request signal or the HTTP status alone.** The opener's request signal can still be live while control already refuses its lease, so the opener would retry first and the joiner would join that second failing flush; and a cancellation that reaches an append control already admitted answers 503, not 403.

## Consequences

- A broker call outside any bound request, or a write in a batch or loop that another request started, carries a capability other than the caller's own, and control refuses it when that lease has ended; a refused write stays queued for the next flush. Work that one request starts and that later serves other requests keeps the capability of the request that started it: the agent driver that a prompt starts also processes prompts sent while it runs, and deferred work such as a session title or a goal round runs under its creator's capability. When control cancels only that lease while the worker keeps running, the work's later direct broker calls are refused.
- The session writer is the lease of the session's last hydration or append. After a completed turn this can be a request lease that ended before a restart, and then the [restarted-worker writer handoff](../architecture/2026-11-09-restarted-worker-writer-handoff.md) is not needed; it is needed when a retained lease, such as a prompt's, made the last write. A native browser scenario that restarts after a completed turn does not prove the handoff; writer-handoff.spec.ts covers it.
