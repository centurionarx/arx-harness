# Agent Note: Gates bloqueantes de Windows executadas via Wine em runners Linux

Status: implemented
Archived: 2026-08-08

[English](2026-07-27-wine-windows-gates-experiment.md) | Português

## Problema

A lane de Windows dos pull requests existe para provar as duas superfícies win32 bloqueantes (o build do workspace e o site de produção) e rodava no `windows-2025` hospedado, o job mais lento da matriz obrigatória: 7 a 9 minutos contra 1,5 a 2,5 dos jobs Linux, de modo que os custos de boot, de setup e de sistema de arquivos da VM Windows dominavam o caminho crítico de todo pull request.

A pergunta que o experimento respondeu: um runner Linux comum consegue produzir um sinal win32 equivalente para as superfícies bloqueantes no tempo de relógio do Linux, de modo que nenhuma VM Windows fique no caminho dos pull requests?

## Decisão

O job `windows` obrigatório dos pull requests em [ci.yml](../../../../.github/workflows/ci.yml) (`windows node 24 / wine blocking`) executa os comandos das gates bloqueantes em `ubuntu-latest` sob o Wine com binários Windows reais: um Node.js win-x64 verificado por checksum executa `tsc -b`, `tsdown` e o build de produção do VitePress, de modo que os ramos win32 da toolchain (tratamento de caminhos com barra invertida, semântica de spawn do `CreateProcess`, carregamento PE de `@esbuild/win32-x64` e os addons `.node` MSVC do rolldown/rollup) de fato são executados. O job `serial-windows` do master fica intocado: o inventário completo de kernel nativo, incluindo as gates observacionais de portabilidade que esta lane não executa, continua rodando no `windows-2025` real a cada push no master.

As dependências são instaladas nativamente no Linux com `supportedArchitectures` estendido para win32-x64, o que materializa os pacotes de plataforma Windows no mesmo store; a camada de cmd-shim é contornada invocando diretamente o entrypoint JavaScript de cada ferramenta, os mesmos processos de que o `run-gates` acaba fazendo spawn. `nodeLinker: hoisted` é essencial, não estilístico: um protótipo independente manteve o layout isolado padrão do pnpm (incluindo uma reinstalação offline fiel pelo pnpm de Windows sobre um store pré-carregado no Linux), e o Node de Windows sob o Wine ainda assim não conseguiu resolver `@esbuild/win32-x64` nem carregar o prebuild do koffi pela cadeia de symlinks isolada, falhando antes que qualquer gate do repositório rodasse. Um layout plano com arquivos reais é o que torna as gates alcançáveis; a fixação por checksum do protótipo foi adotada, enquanto seu objetivo de o pnpm de Windows instalar a árvore foi explicitamente abandonado (o contrato de instalação continua sendo testado no Linux aqui).

A lane mantém o tempo de relógio dos jobs Linux de CI por meio de quatro alavancas: o cache do store do pnpm atualizado pelo master (somente restauração, mesma chave dos jobs Linux), o provisionamento do Wine (instalação via apt, download do Node de Windows, `wineboot`) rodando em paralelo com `pnpm install`, as duas superfícies bloqueantes rodando em paralelo (a mesma disposição que o `run-gates` dá a elas no Windows nativo) e um cache de arquivos do apt com chave na imagem do runner, semeado a partir do master pelo job `wine apt cache`, de modo que todo pull request restaura a partir do escopo do branch padrão.

A lógica das gates vive em um único script, [scripts/wine-windows-gates.sh](../../../../scripts/wine-windows-gates.sh): o job do ci.yml provisiona o estado do runner (caches, Wine via apt) e o chama, e a gate local opcional `pnpm run check:windows-wine` roda o script idêntico em uma máquina de desenvolvimento que tenha o Wine instalado. É uma única implementação, de modo que reproduzir localmente uma lane de CI vermelha não exige tradução entre ambientes. A gate local é uma ferramenta de diagnóstico, não uma verificação de rotina: rode-a apenas ao investigar uma falha conhecida relacionada ao Windows; a CI é dona do sinal win32 do dia a dia, e [dsh-pre-push-checks](../../../skills/dsh-pre-push-checks/SKILL.md) nunca a seleciona. O script nunca altera o working tree: ele faz um snapshot dos arquivos rastreados mais os não rastreados e não ignorados em um diretório temporário, aplica os overrides de pnpm específicos do Wine apenas ao snapshot e instala ali contra o store compartilhado; o prefixo do Wine e o zip do Node de Windows verificado por checksum persistem em `.cache/wine-windows/`, de modo que as reexecuções locais pulam o provisionamento, com um fallback offline para o zip em cache mais recente quando nodejs.org está inacessível.

Cinco restrições de ambiente moldam a execução na CI e a local, cada uma descoberta como uma execução vermelha: o pacote `wine64` do Ubuntu sozinho não coloca nada no PATH (instale `wine`, o dispatcher); o Node sob o Wine não consegue ligar o stdio aos pipes de quem o chama (`Socket open EBADF` no bootstrap: toda invocação roteia o stdio por um arquivo); o Wine não resolve o caminho real (realpath) dos symlinks Unix do layout isolado do pnpm (o layout hoisted acima); o Wine do macOS também expõe os links hoisted do workspace como diretórios comuns, então o agregado de testes do cliente inclui toda declaração de módulo CSS local ao pacote em vez de depender dos realpaths de project references; e o Wine não consegue criar symlinks do Windows (`ENOTSUP` vindo do `linkVue` do VitePress: o link `vue` é criado no lado do host antes da gate).

## Resultados medidos

Medido em 2026-07-27, com caches quentes, gatilho de pull request, `ubuntu-latest` padrão de 2 núcleos: 2m46s de ponta a ponta (setup e restaurações de cache ~17s, instalação e provisionamento em paralelo 33s, gates em paralelo 110s) contra 1,5 a 2,5 minutos dos jobs Linux de CI e 7 a 9 minutos do job `windows-2025` substituído. Uma execução com cache frio paga aproximadamente um minuto a mais. Uma perna de benchmark de 8 núcleos foi definida durante o experimento, mas nunca saiu da fila do pool restrito `dsh-ubuntu-*`; o número do runner padrão atingiu a meta, então nenhuma máquina maior é usada.

## Alternativas consideradas

**Manter o job de pull request no `windows-2025` hospedado (status quo).** Não há nada de errado com o sinal dele, apenas com a latência: 7 a 9 minutos para dois comandos de build, o job obrigatório mais lento da matriz. Ele sobrevive como a referência serial do master, onde a completude importa mais do que a latência.

**Um guest Windows completo sob QEMU/KVM dentro do runner Linux.** Kernel NT real, portanto fidelidade total, incluindo NTFS insensível a maiúsculas e minúsculas e ConPTY, mas com dezenas de minutos de download de imagem e instalação não assistida antes de a primeira gate rodar (40m19s medidos de ponta a ponta no branch de experimento irmão `exp/kvm-windows-ci`). Só é promovível com cache de imagem de disco, que pressiona o orçamento de cache do Actions.

**O pnpm de Windows realizando a instalação sob o Wine.** A variante de maior fidelidade desta mesma ideia: MinGit e pnpm preparados dentro do prefixo, um prefetch no Linux preenchendo o store e então `pnpm install --offline` executado pelo Node de Windows, de modo que o próprio contrato de instalação seja executado como win32. Ela chegou à instalação, mas não às gates: a rede do Wine não conseguiu alcançar o registry diretamente, e o layout isolado de `node_modules` derrotou a resolução dos pacotes de plataforma Windows mesmo depois de uma instalação offline limpa. Esta lane abre mão dessa fidelidade (layout hoisted, instalação no lado do Linux) para alcançar as gates; os dois registros são metades complementares do mesmo veredito.

**Lanes de semântica de sistema de arquivos no Linux (ext4 com casefold, lint de nomes de arquivo).** Capturam a classe de quebra de Windows de maior frequência a custo quase zero, mas não provam nada sobre binários win32. Explorada como o branch de experimento irmão `exp/casefold-windows-ci`; complementar a esta lane, e não concorrente dela.

**Contêineres Windows.** Impossível: contêineres Windows exigem um kernel de host Windows; um runner Linux hospedado não consegue executá-los.

**Abandonar a lane de Windows.** Rejeitada, porque win32 é um alvo de produto de primeira classe: os módulos de DACL e de namespace durável baseados em koffi, as sessões PTY baseadas em ConPTY e a política de caminhos do Windows são todos entregues em `packages/`.

## Consequências

O veredito de Windows de todo pull request agora chega no tempo de um job Linux, em capacidade padrão gratuita, e nenhuma alocação de VM Windows fica no caminho crítico dos pull requests; `all checks passed` consome o mesmo job id `windows` de sempre.

O que a troca custa: o Wine reimplementa o Win32 sobre um ext4 sensível a maiúsculas e minúsculas. A insensibilidade a maiúsculas e minúsculas do NTFS, as DACLs reais, o ConPTY e a semântica de durabilidade após falha não são provados aqui, e o inventário observacional de portabilidade (duplicação, publint, tipos node-next, invariantes de pacotes construídos no win32) deixa de rodar por completo nos pull requests. A referência `serial-windows` do master é dona de tudo isso: um pull request verde no Wine ainda pode falhar na execução de kernel nativo do master, e esse modo de falha é aceito como pós-merge. A lane também herda as divergências específicas do Wine como estrutura permanente do job (stdio roteado por arquivo, o link `vue` no lado do host, o layout hoisted), de modo que uma futura mudança de toolchain que dependa da semântica do layout isolado ou da criação de symlinks dentro do processo aparecerá aqui primeiro como uma falha do Wine, e não como uma falha de produto, e a triagem precisa classificá-la como tal. Se execuções vermelhas do Wine voltarem a ocorrer sem causa no produto, o fallback registrado é reverter o job `windows` para a definição `windows-2025` anterior ao Wine, preservada no histórico do git.
