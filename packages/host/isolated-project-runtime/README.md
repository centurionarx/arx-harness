# Isolated project runtime

Reference for the `isolatedProjectRuntime` provider.

The adapter carries existing ApiProxy requests and event frames to an operator-configured supervisor. It refuses execution without an endpoint and has no local host fallback. Anonymous, restricted first-password, MASTER-ADMIN, blocked and stale authorities cannot dispatch project work.

## Configuration

`endpoint` is a credential-free HTTPS origin, configured together with `credentialRef`. The adapter resolves only that reference through the existing credential provider for each operation. Browser cookies, bearer credentials and Origin headers are excluded from worker requests. `fixtureLoopback` permits HTTP only for an explicitly configured disposable loopback fixture.

`requestTimeoutMs`, `cancellationTimeoutMs`, `maxRequestBytes` and `maxResponseBytes` are required. `requestTimeoutMs` bounds a whole unary exchange but only the response headers of an event stream; afterwards the lease and the downlink signal end the stream. A workspace-scoped unary exchange and the sub-stream attach that precedes it share one `requestTimeoutMs`: a slow attach shortens the time left for the exchange. Unary responses and individual SSE frames obey the response byte limit. Redirects are refused.

`cancellationTimeoutMs` bounds each cancellation request until its quiescent receipt. Cancellations of one user are sent in parallel, each with its own deadline. The supervisor must bound every worker stop and kill the worker's process tree at that bound, and `cancellationTimeoutMs` must exceed, with margin, the longest time the supervisor then takes to deliver a receipt. Control cannot read the supervisor's stop bound; the operator sets both values. The 5000 ms that the test fixtures configure is a test value.

## Authority and protocol

Every admitted payload uses the same browser-safe method schema registry as the existing ApiProxy fetch boundary. Invalid method payloads return the existing `bad-request` business receipt before dispatch; unknown payload fields are refused in the authenticated profile. The fixed request allowlist excludes control-plane settings, credentials, native dialogs, host exit and arbitrary preset installation. Resource references are checked against the authoritative identity sidecar. Creation requires an owned workspace and a control-generated session id; caller cwd, path and preset fields cannot select a host execution context.

The exact server-owned method policy separates active mutations from queries. Automatic `host.describe`, session listing/history, subagent refetch, reconnect, read-only Remotes and event streams do not renew idle even when their transport uses authenticated POST. `session.create` with an existing owned session id is a passive resume; creation without a session id is eligible only after the control-issued allocation and matching worker receipt. A successful active RPC still requires current authority, grant, owner references and an unexpired lease before renewal and again after its durable activity commit. Worker progress, model/tool callbacks and broker persistence do not renew the user session.

A new `session.create` keeps registration lazy until the worker opens the new session and returns the matching allocation receipt. Control then durably commits its canonical empty header before external success or idle renewal. The history is immediately readable with sequence zero and no invented events. Commit failure, cancellation or runtime shutdown rejects success; an admitted write still finishes. Existing-session resume preserves its original lifecycle.

Before live Agent creation, the trusted worker resolves the already allocated header through the closed, read-only `creation-header` broker operation. Control returns only current owned index metadata after storage-grant, owner and lease revalidation; it reads no log and materializes no artifact. The worker validates the assigned id, workspace cwd, preset and format version and uses the control creation timestamp. Browser payloads cannot provide that metadata. Cancellation and revocation refuse its receipt, and this passive read never renews idle.

Canonical Typert business results keep their existing codecs. `commands/execute` renews only for its `result.kind: success`; unresolved commands and command errors remain passive. Feedback mutations require their inner `ok: true`, so compare-and-set and validation refusals cannot renew through an outer RPC success. A correlated `/api/respond` renews only after `accepted: true` while its original pending lease remains valid, and only the responding authentication session is renewed.

Worker requests carry an opaque operation id, owner user id, security revision and selected project/workspace ids. The worker-history broker accepts only a capability whose lease carries a scope; an unscoped lease cannot read or write any history. A session has one writer: the worker that last hydrated or appended it, under the lease of that request. When a different worker id asks to hydrate a session whose writer lease is still live, control treats that worker as restarted: it applies the same scope and owner checks, cancels the old lease by its operation id, and moves the writer only after that cancellation ends with a quiescent receipt, whose request is bounded by `cancellationTimeoutMs`; concurrent requests share one cancellation. Control reads the writer again after those checks and cancels it only while the same worker id and lease are still the writer and that lease is still live, so a lease that ended with a quiescent receipt during the checks, or a writer that moved to a newer lease, receives no cancellation; an append by the old worker under the same lease leaves the writer unchanged. A missing receipt refuses the hydration and closes the adapter like any other missing receipt. A hydration request that is itself aborted stops waiting, and the shared cancellation continues. The same worker id, or a worker presenting the writer lease itself, never triggers this cancellation, and appending still requires a prior hydration. The supervisor must give every worker process it starts, including a restarted or replacement process, a worker id it has never used: control detects a restart and decides between a cold and a warm hydration by comparing worker ids, so a reused id makes a restarted worker indistinguishable from the stopped one. The handoff relies on the cancellation receipt contract below: a supervisor that confirms an operation id it does not know must ensure that no process of any earlier worker that could have run that operation can still run. The worker boundary binds a history capability only from workspace-scoped requests. A broker call made by such a request or by asynchronous work it starts, such as its stream frames or the turn a prompt starts, carries that request's own capability; a write it only awaits through a session flush or loop that another request started carries that request's capability, and when control refuses a write that carried another request's capability while the request's own operation is still live, the boundary flushes the session once more under its own. A refusal of the request's own capability, such as a failed durable append under it, fails the request. A call outside any bound request, such as at worker mount or for an unscoped request, carries the latest bound capability. The boundary refuses a request whose signal is already aborted before any worker work starts. The final authority check occurs after credential resolution and before fetch. Supervisor responses echo `x-arx-operation-id`; `x-arx-quiescent: true` releases a finished lease. A background operation retains its lease until supervisor cancellation.

Cancellation posts to `/_arx/operations/{id}/cancel` and requires a matching operation id with `quiescent: true`. The path operation id selects the target; scope headers do not. The supervisor verifies the bearer credential and that `x-arx-user-id` owns the operation, stops only that operation, and refuses another user's operation. An unknown or finished operation id returns `{ operationId, quiescent: true }`; a finished id is confirmed only to its owner and an unseen id to the caller. Every confirmed id is tombstoned: later requests carrying it are refused. The quiescent receipt is sent only after the operation's handler has finished, and no worker work can start from that operation afterwards. Revocation listeners are asynchronous and reach quiescence before the identity mutation acknowledges. Resource deletion uses its separate ownership-deleted event, also awaiting cancellation before ACK while preserving the authentication cookie and security revision. A receipt that is missing, invalid or later than `cancellationTimeoutMs` closes the adapter for every user until the control process restarts. When that happens control logs one error with the operation id, the trigger of that cancellation, the class of the error and, for a `WebIdentityError`, its code: `RUNTIME_QUIESCENCE` (a non-ok response, or a JSON receipt that does not confirm the operation as quiescent), `RUNTIME_LIMIT` (a receipt larger than `maxResponseBytes`) or `RUNTIME_UNAVAILABLE` (the supervisor credential did not resolve). A receipt that is not JSON logs `SyntaxError` with no code. The message, cause and stack of the error are never logged, because they can carry the supervisor credential or response bytes; no session event records the closure. The trigger is `authority-invalidated` (account status, grant or revision change), `ownership-deleted` (a project, workspace or session was deleted), `session-expired` (one login expired or logged out), `disposal` (the adapter is shutting down), `quiesce-call` (a direct `quiesce()` call), `writer-handoff` (a restarted worker hydrating a session), `request-failed` (a request or sub-stream attach failed or was aborted after its lease existed) or `downlink-closed` (a mux or host downlink ended). Process interruption never triggers automatic replay of external work.

## User-level operations across workspace workers

Control answers user-level operations; no supervisor merges anything. `host.describe` is answered by control without a worker: control version, empty `cwd` and `home`, no attached sessions, `canOpenPath: false` and no model selection. Each mux or host downlink is one merged stream over one workspace-scoped sub-stream per attached workspace. At open, control attaches the workspaces that have a live lease of that user; before forwarding a workspace-scoped request, `dispatch()` attaches that workspace's sub-stream to every open downlink of the user and waits for its response headers within the request's `requestTimeoutMs` and caller signal. Exposure is checked again when a frame leaves the downlink queue, so a frame queued before quiescence or closure is never published. A worker's own mux baseline replays its subscribed sessions, pending questions and approvals, queues and jobs when its sub-stream attaches. Order holds within one worker and is not defined across workers. Any sub-stream end or failure ends the whole downlink and cancels every sub-lease, each with its own receipt; the client reconnects. A downlink over N workspaces therefore needs N receipts when it ends, and any one of them missing closes the adapter. Pending replies belong to the sub-lease of the worker that asked. Quiescence and session expiry close idle downlinks directly; attached downlinks end through their cancelled sub-leases.

Unscoped `session.list`, `session.search` and `workspace.list` are answered by control: it reads the user's grouped workspaces in display order from the project index, sends one workspace-scoped request per workspace and concatenates the owner-filtered items in workspace order; search keeps each worker's ranking within its result limit. Titles, projections, `running`, session order and archived sessions come from those workers. One failed request refuses the whole answer. Archived sessions in `workspace.list`, `workspace.archiveSession` and `host/archived-sessions-changed` are the union of every workspace control has seen for the user, limited to sessions the user still owns. `workspace.insertBefore` is answered by control: it checks ownership of both workspaces, stores the complete order in the project index, one move per user at a time, and sends `host/workspace-order-changed` on the user's host downlinks after revalidating each receiving login; worker order frames are dropped. An identity failure while notifying can follow a committed order; repeating the same move is safe.

The existing SSE carrier parses mux and host frames. Owner references are verified before emission against the sub-stream's workspace, so a frame naming another workspace is dropped; foreign aggregate rows are filtered, and generic remote host events are refused. Logout, security revision changes and disposal abort transports and cancel retained supervisor leases.

The private worker-history RPC has a closed `list-snapshots` operation. Control observes one actual provider metadata scan, filters every session through current owner/workspace membership and revalidates authority before returning headers and source-qualified revisions. Worker `list` and `listSnapshots` consume that receipt without per-session global scans. Individual snapshot reads retain complete event validation and before/after `readRevision` checks. Index rows never supply revision tokens.

## Model Experience

### Existing isolated agent execution

#### What the model sees

The adapter contributes no system prompt or tool schema. Its `session.prompt` carrier preserves the existing worker composition, model routes, tools and logged session events.

#### Token effect

Zero direct request-token effect.

#### KV Cache effect

The carrier adds no model-visible prefix and preserves the existing worker composition's cache behavior.

## Known Limitations and Deferred Work

- HTTP fixtures prove request ownership, response filtering and cancellation of disposable child processes. They do not prove distinct VM/UID, filesystem mounts or network isolation.
- `cancellationTimeoutMs` bounds only the supervisor cancellation request. Resolving the supervisor credential before it, and waiting for the cancelled lease's own request handler and queued broker work after it, have no deadline.
- The native test supervisor's `stopTimeoutMs` reproduces the timing of a bounded worker stop with a forced kill; it cannot kill an in-process worker, and without the option its stop has no deadline.
- The trusted supervisor must isolate worker filesystem, processes and egress and keep its credential outside untrusted code. Internet activation requires verified supervisor deployment.
- Every unscoped listing or search sends one request to each workspace worker of the user and wakes every worker, and attached sub-streams keep those workers busy while a downlink is open; the first request for a workspace adds one stream round trip; one broken worker ends the user's downlink and forces client reconnects ([Agent Note](../../../.agents/notes/implemented/architecture/2026-11-06-multi-worker-routing-of-user-level-operations.md)).
- `skill.list`, `agentPreset.list`, `llm.providers`, `llm.models` without a session and `web.providers` remain unscoped worker requests: a supervisor routes them only for a user with one worker, and their history calls carry the latest bound capability.
- A broker call outside any bound request, or a write in a batch or loop that another request started, carries a capability other than the caller's own; control refuses it (403) when that lease has ended. A refused write stays queued for the next flush, and a request whose own flush is refused twice answers an error. Work that one request starts and that later serves other requests, such as the agent driver a prompt starts, which also processes prompts sent while it runs, or deferred work such as a session title or a goal round, keeps the capability of the request that started it; when control cancels only that lease while the worker keeps running, that work's later direct broker calls are refused.
- Arbitrary host-path workspace creation and control-plane API methods are unavailable in authenticated project mode.

- `session.fork` requires the worker persistence broker to allocate and register the child id in the control domain before worker effects. A composition without that broker fails closed; local fork payloads remain unchanged.
- The worker-to-control broker requires a separately deployed trusted supervisor, isolated worker allocation and protected broker credentials. Disposable provider compositions verify the protocol but do not establish production isolation or activation.
