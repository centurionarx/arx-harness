# Documentação bilíngue

[English](README.md) | Português

A documentação deste repositório é lida por pessoas e agentes dentro e fora da empresa, então todo documento no escopo é mantido em inglês e português do Brasil. Esta página define o plano de pareamento, as verificações, o escopo e as exclusões; [translation-rules.md](translation-rules.pt-BR.md) define como traduzir; [terminology.md](terminology.md) é a fonte da verdade terminológica. O trabalho de agente rotineiro segue o caminho leve em [docs/AGENTS.md](../AGENTS.md); o fluxo estendido [.agents/skills/arx-translate-docs](../../.agents/skills/arx-translate-docs/SKILL.md) fica disponível apenas por invocação explícita do usuário.

## O plano de pareamento

- **Os dois idiomas têm autoridade igual.** Um documento pode ser escrito e revisado primeiro em qualquer um dos idiomas — uma nota de agente escrita primeiro em português é tão legítima quanto uma em inglês — e o parâmetro é traduzido a partir daquele lado. Nenhum arquivo prevalece sobre o outro; o que os vincula é que devem dizer a mesma coisa.
- **Um par são três arquivos irmãos.** O `foo.md` inglês, o `foo.pt-BR.md` português e um registro de consistência `foo.i18n.yaml`, todos no mesmo diretório. Sem diretórios de locale, sem repositório de tradução separado, sem arquivos bilíngues intercalados. Os pares entram inteiros: um PR nunca aterrissa um idioma sem os outros dois arquivos.
- **O registro de consistência.** `foo.i18n.yaml` guarda o blob hash git completo de cada lado na última vez em que os dois lados foram confirmados como dizendo a mesma coisa:

  ```yaml
  foo.md: 3f786850e387550fdab836ed7e6dc881de23001b
  foo.pt-BR.md: 89e6c98d92887913cadf06b2adb97f26cde4849b
  ```

  Blob hashes, não hashes de commit, para o registro ser computável para arquivos editados no mesmo PR (`git hash-object foo.md`) e a consistência ser uma comparação pura de conteúdo. O `--write` armazena esses snapshots no banco de objeto Git local antes de registrar, inclusive o conteúdo não commitado da worktree, e fixa cada blob distinto numa ref endereçada por conteúdo `refs/arx/translation-pairing/snapshots/` para que a coleta de lixo não invalide um ponteiro de recuperação registrado. Os hashes registrados, portanto, recuperam o texto exato do último estado confirmado de qualquer dos lados: um par fora de sincronia é atualizado com um patch mínimo no parâmetro contra o diff do lado editado — nunca retraduzindo arquivos inteiros. O trabalho rotineiro faz esse patch diretamente; quando o usuário invoca explicitamente o fluxo estendido, `pnpm run gen-translation-brief <pair>` pode montar a atualização na granularidade segura mais estreita e o `--apply` pode aplicar uma mudança só de code fence após validação estrutural ([nota de agente de atualizações com briefing](../../.agents/notes/implemented/process/2026-07-26-briefed-minimal-translation-updates.md)). Depois de alinhar o par, `pnpm run verify-translation-pairing --write <pair>` reregistra os dois hashes; esse diff do yaml é o ato revisável de confirmar consistência, razão pela qual o `--write` exige nomear os pares confirmados (`--write --all` é a forma explícita para o corpus inteiro).

  Quando dois branches contêm confirmações válidas do mesmo par, o merge driver Git `arx-translation-pairing` instalado compõe um novo registro apenas se o merge textual do Git tiver sucesso para os dois trios de blobs registrados e o par mesclado mantém os switchers exigidos e a assinatura estrutural. O arquivo português deve manter seu backlink em inglês; uma fonte em inglês autoral deve manter seu link português, enquanto uma fonte gerada listada fica isenta. Qualquer estrutura que o driver não consiga verificar permanece um conflito comum; `pnpm run resolve-translation-pairing-conflicts` aplica a mesma operação fail-closed a um merge que já parou, registra a staging cada registro de pareamento seguro e sai com erro quando outros conflitos de pareamento permanecem. A [nota de agente de merges automáticos de pareamento](../../.agents/notes/implemented/process/2026-08-08-automatic-translation-pairing-merges.md) controla o mecanismo e as alternativas.
- **Switcher de idioma.** O arquivo português sempre volta logo após o H1 com `[English](foo.md) | Português`. Um arquivo em inglês autoral retribui com `English | [Português](foo.pt-BR.md)`; uma fonte em inglês gerada listada omite essa linha para permanecer byte-idêntica à saída do gerador. Um README publicado fora do GitHub, como metadados do PyPI, pode usar a URL canônica `https://github.com/centurionarx/arx-harness/blob/master/<repository-path>` para o mesmo parâmetro, para o switcher resolver lá também.
- **A estrutura espelha o parâmetro.** Profundidades e ordem dos cabeçalhos, tipos de lista, inícios de listas ordenadas, contagem de itens, contagem de linhas e colunas de tabelas, destinos semânticos de links com sufixos de query/fragmento exatos e code blocks verbatim correspondem um a um no par. Quando um link relativo aponta para o corpus bilíngue ativo, o lado inglês usa seu caminho `.md` e o lado português usa seu caminho `.pt-BR.md`. Um parâmetro ausente nesse corpus é um erro de completude do par, e não um fallback; destinos fora do corpus ativo mantêm o caminho escrito. Veja [translation-rules.md](translation-rules.pt-BR.md) para as regras de preservação completas. As gates de Markdown existentes se aplicam aos arquivos `.pt-BR.md` sem mudanças (`verify-md-wrap`, `verify-md-links`).

## A gate: verify-translation-pairing

`pnpm run verify-translation-pairing` (parte do `doc-sync`, que quem contribui roda localmente para mudanças de documentação e o CI roda exaustivamente) aplica o plano mecanicamente:

1. Todo documento no corpus ativo tem um par completo. A descoberta de README não distingue maiúsculas no basename, então `missions/readme.md` está no escopo junto com as outras raízes de documentação; um documento no escopo mas fora do corpus ativo não deve nada até o corpus crescer.
2. Todo artefato de par que existe é completo e consistente: os três arquivos presentes, o blob hash atual de cada lado igual ao registrado (editar qualquer lado sem reregistrar o par fica vermelho), o lado português e toda fonte em inglês autoral carregam os switchers de idioma (fontes em inglês geradas listadas ficam isentas), todo link relativo comum usa o locale de destino do lado da fonte e as assinaturas estruturais coincidem em ordem — profundidades dos cabeçalhos, code blocks verbatim (info string e conteúdo), contagens de linhas e colunas de tabelas, tipos de lista, inícios de listas ordenadas, contagens de itens e destinos semânticos de links com sufixos exatos de query/fragmento, exceto o switcher.
3. Arquivos listados como `excluded` não têm `.pt-BR.md` nem `.i18n.yaml` de forma alguma. Notas de agente congeladas sob `.agents/notes/archived/` ficam fora desta gate evolutiva; o verificador dedicado delas exige e sela o trio completo existente.

As gates de código orientadas à fonte consomem uma sequência exata de fences `.pt-BR.md` como derivada do irmão sem sufixo em vez de compilar ou materializar o mesmo código duas vezes. A sequência deve coincidir em comprimento, ordem, tipo de fence e corpo byte-exato; caso contrário, as duas cópias permanecem verificadas de forma independente e a gate de pareamento reporta a divergência estrutural.

`pnpm run verify-translation-pairing --list` imprime o estado de pareamento atual de cada documento no escopo — missing, out-of-sync, ok ou fora do corpus ativo. Nunca falha; as linhas `missing` e `out-of-sync` identificam violações que a verificação normal rejeita.

`pnpm run verify-translation-pairing <pair...>` verifica apenas os pares nomeados — qualquer um dos três arquivos do par (ou o stem) o nomeia — para que um loop de atualização verifique o próprio par em segundos em vez de reescanear o corpus. A forma sem argumentos, para o corpus inteiro, é o que `doc-sync` e o CI executam; um verde pontual nunca a substitui no nível do PR.

A regra prática que esta gate cria: **quando um PR edita qualquer lado de um documento pareado, o mesmo PR atualiza o parâmetro diretamente em uma passada guiada pela terminologia e reregistra o par com `--write <pair>`**, exatamente como a regra doc-sync existente do repositório para código e READMEs. Um PR que deixa um par fora de sincronia fica vermelho no CI.

O limite da gate, dito com clareza: **uma gate verde significa que o par foi confirmado consistente nesses conteúdos exatos, e não que a confirmação em si seja sólida.** Ela verifica hashes e estrutura Markdown; não pode julgar se os dois lados de fato dizem a mesma coisa, nem se a redação é precisa, bem terminológica e natural — essa é a metade do contrato que fica com o revisor, segundo [translation-rules.md](translation-rules.pt-BR.md). Um par reregistrado com um parâmetro descuidado passa na gate; não deve passar na revisão.

## Escopo e exclusões

**Escopo**: os documentos CONTRIBUTING e BRAND_GUIDELINES raiz, todo README fora de vendor e todo documento ativo sob `.agents/notes/**`, `docs/**` e `python/**`. O casamento de README não distingue maiúsculas no basename e cobre diretórios futuros sem outra edição do manifesto. Árvores de dependências e de saídas de build ignoradas, além da árvore congelada `.agents/notes/archived/`, são exclusões da descoberta, não fonte de tradução em evolução.

Referências e gráficos em inglês gerados participam do pareamento quando existe um parâmetro português revisado. Seus geradores continuam sendo a fonte da verdade em inglês, e as gates de frescor e de pareamento aplicam seus invariantes de forma independente; uma regeneração que muda o inglês deixa o par fora de sincronia até que o parâmetro português revisado seja atualizado e reregistrado. Um gerador que controla os dois lados, como o gerador de regiões de subsistema do Cordis, projeta os caminhos de documentos pareados para cada locale de saída mantendo todos os outros bytes gerados iguais. Fontes em inglês geradas omitem o switcher de idioma que as fontes autorais comuns carregam, porque adicioná-lo deixaria o gerador obsoleto; seus parâmetros português ainda apontam de volta para a fonte em inglês. O parâmetro português de uma página gerada pode reescrever apenas declarações autorreferentes de geração e manutenção que de outro modo seriam falsas para a tradução revisada; todo o conteúdo técnico permanece sujeito às regras comuns de fidelidade.

**Exclusões** (nunca pareadas; a gate rejeita um `.pt-BR.md` ou `.i18n.yaml` para elas):

- [cordis-api/inherited.md](../cordis-api/inherited.md) — gerada sem um parâmetro português revisado, então ambos os locales do site projetam a fonte em inglês.
- `docs/AGENTS.md`, `.agents/notes/**/AGENTS.md` e os symlinks de instrução `CLAUDE.md` — instruções de agente, mantidas apenas em inglês como o `AGENTS.md` raiz.
- `docs/i18n/terminology.md` e [style-samples.md](style-samples.md) — ambos bilíngues por construção.
- [translation-prompt.md](translation-prompt.md) — o template de prompt do pipeline automatizado; o corpo é consumido pela máquina verbatim, então uma tradução pareada mudaria o comportamento do pipeline.
- `.agents/notes/archived/` — trios históricos congelados. [`verify-archived-agent-notes`](../../scripts/verify-archived-agent-notes.ts) valida a completude deles e sela o conteúdo; a manutenção de tradução nunca os reescreve.

**Corpus ativo**: os globs de `included` em [scripts/translation-pairing.manifest.json](../../scripts/translation-pairing.manifest.json) nomeiam os documentos no escopo cujos pares são exigidos agora; ausente, todo documento no escopo é ativo. Todo documento atual ou futuro no corpus ativo deve entrar como um par bilíngue completo, e o corpus cresce estendendo `included` no PR que traz o par — não há data de corte nem classe específica de README. Um par que existe fora do corpus ativo continua verificado inteiro, e o lado português dele aponta para documentos fora do corpus pelo caminho `.md` escrito. O site projeta o lado português na locale raiz exatamente para o corpus ativo e a fonte em inglês no restante. `excluded` lista os documentos que nunca pareiam.

## Divisão do trabalho

Os parâmetros rotineiros são atualizados diretamente pelo agente de trabalho em um tiro e uma passada depois de carregar [terminology.md](terminology.md); ele não invoca uma skill de tradução, não gera briefing, não roda uma passada de revisão de tradução separada nem delega a um subagente. O fluxo estendido [arx-translate-docs](../../.agents/skills/arx-translate-docs/SKILL.md) mantém esses mecanismos mais pesados para invocação explícita do usuário. A gate verifica a completude dos pares, os hashes registrados, o backlink português e o switcher da fonte autoral (com a exceção documentada de fonte gerada) e a assinatura estrutural documentada. A revisão ainda é dona da qualidade da tradução, da terminologia e dos requisitos estruturais que a assinatura não codifica. O contrato de prompt é executável: [scripts/translation-prompt.ts](../../scripts/translation-prompt.ts) renderiza o template commitado (terminology injetada; o template carrega suas próprias regras calibradas) em qualquer direção e faz o parse da resposta de três seções, enquanto `verify-translation-prompt` exercita as duas direções de render e o exemplo checked-in no `doc-sync`.
